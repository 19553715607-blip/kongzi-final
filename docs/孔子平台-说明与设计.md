# 第一篇　平台说明

> 让全球用户用母语、用游戏、用对话，亲身体验中华儒家文化。

---

### 一、平台是什么

「孔子」是一个**面向全球的儒家文化数字化交互平台**。它不只是把《论语》翻译成多语言放在网上，而是把儒家文化**做成可对话、可游戏、可分享、可被海外机构嵌入使用**的活态平台。

一句话：**让"读论语"变成"和儒家对话、用六艺修身"。**

---

### 二、为什么做

传统的中华文化海外传播有三个痛点：

1. **只能"读"不能"用"** — 经典文本翻译再准，海外用户也只是被动接收
2. **缺乏沉浸感** — 概念抽象（仁、礼、中庸），没有体验入口
3. **缺乏对话感** — 儒家与基督教、伊斯兰、现代世俗等其他文明的差异讲不清

我们的解法：用**多智能体 AI + 知识图谱 + 游戏化**，把儒家从「文本」做成「体验」。

---

### 三、给谁用

| 用户群 | 使用场景 |
|---|---|
| **海外高校师生** | 在母语界面查典籍、跟 AI 对话、玩六艺、写论文 |
| **海外文化机构** | 通过开放 API 把儒家语义嵌入自己的网站、App、课程 |
| **国内年轻人** | 短视频流式刷金句、游戏化打卡、与朋友分享 |
| **研究者** | 经典溯源、跨文明比较、知识图谱钻取 |
| **校园终端** | 孔子学院、文化中心的展示屏交互入口 |

---

### 四、核心能力（五个）

#### 1. 智能对话
用 **Qwen-Plus 大模型 + 多智能体协同**回答关于儒家的任何问题。每条回答都绑定经典原文出处（可点击溯源），并给出三项校验评分：文本依据 / 现代发挥 / 文化适配。**5 语**实时切换。

#### 2. 六艺游戏化修身
把古代「礼乐射御书数」做成 6 个独立游戏：
- **礼** — 3D 第三人称庭院「执礼 · 宾至如归」：迎宾次序、揖礼深浅、安席位次、席间照应，考「敬 · 序 · 节」
- **乐** — 32 拍五音填序，体验「和而不同」
- **射** — 3D 射场，反求诸己，连中三发会触发"射不主皮"提示
- **御** — 2D 马车，体验"礼以行之、不极不躁"
- **书** — 三玩法：选字 / 拼字 / 笔顺
- **数** — 滑块公平分配（不患寡而患不均）

每艺都有**关联经典原文解锁**和**五品评级**，所有六艺有总览 + 勋章墙 + 群体排行。

#### 3. 跨文明对话
5 个全球议题（气候 / 技术 / 社会 / 个人 / 治理）下，**2,500 个对话案例**展示儒家与古希腊、基督教、伊斯兰、现代世俗的立场对比。

#### 4. 知识图谱
人物 / 概念 / 篇章 / 命题 / 学派 五类节点的**可视化关系网**，支持邻域钻取与两点最短路径。Neo4j 真实图库后端。

#### 5. 开放接口
海外机构一键申请 API Key，**10,000 次/月**配额。已对接 **8 家高校与文化机构**（Harvard、Stanford、Cornell、Sorbonne、Oxford、Keio、首尔大、旧金山孔子学院）。

---

### 五、体验亮点

- **5 语全栈** — 中 / 英 / 法 / 西 / 阿，不只是界面，AI 回答和典籍都是
- **无登录墙** — 首次访问自动发游客号，进度保留，可后绑邮箱
- **三端响应式** — 桌面 / 手机 / 平板一套代码，触屏游戏单独优化
- **隐私合规** — GDPR / CCPA 数据导出 + 删除一键完成
- **暗黑 / 护眼主题** — 暖调深色，无闪烁切换

### 五、前端设计原则

#### 5.1 多终端策略

| 终端 | 主布局 | 信息密度 | 主交互 |

原型阶段技术路线：**响应式 Web + PWA**，一套代码覆盖三端。

#### 5.2 全球化与多语言

- 界面文案：i18next / vue-i18n
- 经典内容：后端按 `lang` 字段返回译文
- 智能体输出：翻译智能体生成
- 儒家术语三段式：`Ren (仁) — humaneness / benevolence`
- RTL 适配（阿拉伯文等），CSS 用逻辑属性

#### 5.3 面向 Z 世代

**关键洞察 → 设计响应**：

| Z 世代特征 | 设计响应 |
|----------|---------|
| 移动原生、注意力碎片化 | 短内容优先、滑动流 |
| 视觉驱动、反长文 | 卡片、动效、短视频 |
| 反说教、要共鸣 | "AI 不是老师，是同行者" |
| 社交即身份 | 可分享、可二创、有梗 |
| 游戏化预期 | 打卡、成就、等级、勋章 |
| 个性化即基本 | 主题、AI 人格自选 |
| 重视情绪与陪伴 | 治愈感、不评判 |
| 暗黑模式偏好 | 默认提供 Dark / Light / 护眼 |
| AI 原生 | 不解释 AI，直接给体验 |

**核心转向**：从「庄重古典 + 学者气质」→「东方酷感 + 朋友式陪伴 + 轻量游戏化」。

#### 5.4 视觉系统：新东方美学

# 第四篇　后台设计方案

> 配套《平台设计方案》前端（本册第三篇）· 2026-06-05

本文档承接已完成的前端原型（多终端 / 多语言 / 10 类智能体 / 游戏化 8 屏），给出**可落地**的后端设计：服务边界、接口契约、数据模型、智能体编排、RAG 管线、成本与性能、全球部署与合规。

---

### 一、设计原则

1. **统一中台，多端复用**：所有终端（Web / PWA / 平板 / 小程序 / 语音）共用同一套 API，差异只在「终端适配」这一层做投影，不为某个端单独开后端。
2. **可追溯优先**：每一条 AI 回答都必须能映射回原文出处（书·篇·章·句）。这是儒家平台的底线，也是「校验徽章」「依据可点击溯源」前端功能的后端基础。
3. **智能体是手段不是目的**：10 类智能体不等于每次请求 10 次 LLM 调用。多数「智能体」实现为**工具/函数**或**条件分支**，只有需要生成与推理的环节才真正起 LLM。目标：常见问答 P95 首字延迟 < 1.5s。
4. **成本可控**：经典文本是**有限且基本不变**的语料，应大量预计算、强缓存（语义缓存 + 译文缓存 + 概念解释缓存），把贵的 LLM 调用压到真正需要的地方。
5. **无状态服务 + 有状态存储**：业务服务全部无状态、可横向扩展；状态收敛到数据库与对象存储，便于多区域部署。

### 四、对话编排服务（核心）

这是整个后端的心脏，对应前端「智能体可视化」「分层展开」「校验徽章」。

#### 4.1 编排策略：路由 + 并行扇出 + 单次校验

不要把 10 个智能体串成一条 10 跳的链（慢且贵）。采用如下 LangGraph 状态图：

```
            ┌──────────────┐
   输入 ──▶ │  Router/Planner│  轻量模型：识别意图、语言、所需能力、终端
            └──────┬───────┘
                   │  产出执行计划（需要哪些节点）
        ┌──────────┼───────────────┬──────────────┐
        ▼          ▼               ▼              ▼     （能并行的并行扇出）
   ┌────────┐ ┌─────────┐    ┌──────────┐  ┌──────────┐
   │经典检索 │ │知识图谱 │    │概念解释  │  │教学引导  │
   │(RAG)   │ │(Neo4j) │    │(LLM/缓存)│  │(LLM)    │
   └───┬────┘ └────┬────┘    └────┬─────┘  └────┬─────┘
       └───────────┴──────┬───────┴─────────────┘
                          ▼
                  ┌───────────────┐
                  │  合成 Synthesizer│  旗舰模型：基于检索证据生成候选答案（带引用）
                  └───────┬───────┘
                          ▼
              ┌───────────────────────┐
              │ 翻译 / 跨文化转化（条件） │  非中文用户或显式要求时启用
              └───────────┬───────────┘
                          ▼
                  ┌───────────────┐
                  │  校验 Verifier  │  核对每条主张是否有原文支撑，打三项评分
                  └───────┬───────┘
                          ▼
                  ┌───────────────┐
                  │  终端适配 + 追问 │  按设备投影格式 + 生成推荐追问 chips
                  └───────┬───────┘
                          ▼
                       流式输出
```

**智能体的真实实现形态**：

| 智能体 | 实现形态 | 是否起 LLM |
|--------|---------|-----------|
| 总控（Router/Planner） | 轻量 LLM + 规则 | 是（小模型/可缓存） |
| 经典检索 | 向量检索 + 重排函数 | 否（纯检索） |
| 知识图谱 | Cypher 查询函数 | 否 |
| 概念解释 | 缓存命中→直出；未命中→LLM | 多数命中缓存 |
| 教学引导 | LLM（结合用户画像） | 是 |
| 合成/回答 | 旗舰 LLM | 是（主成本） |
| 多语言翻译 | LLM；术语走对照表 | 条件 |
| 跨文化解释 | LLM（带文化语境 prompt 模板） | 条件 |
| 回答校验 | LLM（约束式核对） | 是 |
| 终端适配 | 纯函数（按 device 投影） | 否 |
| 语音 | ASR/TTS 服务 | 否（专用模型） |

> 结论：一次典型中文问答约 **2–3 次 LLM 调用**（路由小模型 + 合成 + 校验），其余为检索/缓存/函数。外文跨文化问答再加 1–2 次。

#### 4.2 流式协议

- 客户端 → `POST /api/v1/chat`，服务端用 **SSE**（或 WebSocket）流式返回。
- 事件类型分离，前端可据此驱动「智能体状态条」「分层展开」「经典卡片」：

```
event: agents      data: {"active":["retrieval","graph","explain"]}   // 点亮智能体色点
event: token       data: {"text":"克己复礼"}                           // 流式正文
event: citation    data: {"book":"论语","chapter":"颜渊","ref":"12.1"} // 经典卡片
event: verify      data: {"textual":0.95,"modern":0.7,"cultural":0.8}  // 校验徽章三评分
event: followups   data: ["礼和仁是什么关系？","现代社会还需要礼吗？"]    // 追问 chips
event: done        data: {"message_id":"...","tokens":1234}
```

#### 4.3 RAG 检索细节

1. **混合检索**：向量召回（语义） + 关键词/BM25（精确术语如人名、篇名） + 图谱召回（概念关联），三路融合。
2. **重排**：用 reranker（或轻量 LLM）对候选句排序，取 Top-K（K≈5）。
3. **证据绑定**：合成节点的 prompt 强制「只能基于提供的证据作答，每个论断标注 `[出处编号]`」，校验节点再核对编号是否真实存在 → 这是降幻觉的关键。
4. **多语言检索**：用户问英文 → 用多语种 embedding 在同一向量空间召回中文原文 → 译文从译文库取，不现翻原文。

### 五、数据模型

#### 5.1 经典内容（PostgreSQL）

核心是把「书→篇→章→句」做成可寻址的树，每个节点带稳定 `ref_id`（如 `lunyu.yanyuan.12.1`），这是全平台溯源的主键。

```sql
-- 典籍
CREATE TABLE books (
  id            TEXT PRIMARY KEY,        -- 'lunyu'
  title_zh      TEXT NOT NULL,           -- '论语'
  title_i18n    JSONB,                   -- {"en":"The Analects","ja":"論語"}
  author        TEXT,                    -- '孔子及弟子'
  era           TEXT,
  sort_order    INT
);

-- 章节（篇）
CREATE TABLE chapters (
  id            TEXT PRIMARY KEY,        -- 'lunyu.yanyuan'
  book_id       TEXT REFERENCES books(id),
  title_zh      TEXT,                    -- '颜渊'
  title_i18n    JSONB,
  sort_order    INT
);

-- 句/段（最小可寻址单元，对应前端"读一读"的五层信息）
CREATE TABLE passages (
  id            TEXT PRIMARY KEY,        -- 'lunyu.yanyuan.12.1'
  chapter_id    TEXT REFERENCES chapters(id),
  ref_label     TEXT,                    -- '论语·颜渊·12.1'
  original_text TEXT NOT NULL,           -- '克己复礼为仁。'
  pinyin        TEXT,                    -- 'kè jǐ fù lǐ wéi rén'
  sort_order    INT,
  concepts      TEXT[],                  -- ['ren','li'] 关联概念
  meta          JSONB
);

-- 译文（多语言，一句多译）
CREATE TABLE translations (
  passage_id    TEXT REFERENCES passages(id),
  lang          TEXT,                    -- 'en','ja','ko'...
  text          TEXT,
  translator    TEXT,                    -- 来源/译者，可信度溯源
  PRIMARY KEY (passage_id, lang, translator)
);

-- 注释（传统注疏 + 现代释义，对应"字词释义"层）
CREATE TABLE annotations (
  id            BIGSERIAL PRIMARY KEY,
  passage_id    TEXT REFERENCES passages(id),
  type          TEXT,                    -- 'classical'(朱熹注) | 'modern' | 'word'
  lang          TEXT,
  source        TEXT,                    -- '朱熹《论语集注》'
  content       TEXT
);

-- 概念本体（对应"概念图鉴"，跨语言术语对照）
CREATE TABLE concepts (
  id            TEXT PRIMARY KEY,        -- 'ren'
  zh            TEXT,                    -- '仁'
  pinyin        TEXT,                    -- 'rén'
  i18n          JSONB,                   -- {"en":"benevolence / humaneness","ja":"仁"}
  school        TEXT,                    -- 学派
  rarity        TEXT,                    -- 'normal'|'SR'|'SSR'（图鉴稀有度）
  definition    JSONB,                   -- 多语言释义
  related       TEXT[]                   -- 相关概念
);
```

> AI 解读（第五层）**不入库为静态文本**，而是运行时由概念解释/合成智能体生成并缓存，避免把"AI 发挥"混进权威经典。

#### 5.2 向量库（Milvus / Chroma）

每个 passage、annotation、concept 切分后入向量库，元数据携带 `ref_id` 便于回链：

```
collection: confucian_corpus
  vector:   embedding (multilingual, 1024d)
  fields:   ref_id, type(passage|annotation|concept), book_id, lang, text
```

#### 5.3 知识图谱（Neo4j）

```
节点：(:Person {id,name})       人物：孔子、颜渊、孟子...
      (:Concept {id,zh,en})     概念：仁、礼、中庸...
      (:Passage {id,ref})       篇章/句
      (:Proposition {id,text})  命题：'克己复礼为仁'
      (:School {id,name})       学派

关系：(:Person)-[:DISCIPLE_OF]->(:Person)
      (:Concept)-[:RELATED_TO {label}]->(:Concept)
      (:Passage)-[:MENTIONS]->(:Concept)
      (:Person)-[:PROPOSED]->(:Proposition)
      (:Proposition)-[:ABOUT]->(:Concept)
```

图谱服务对外提供：①概念邻域子图（前端图谱页）②两节点间路径（"仁和礼怎么连"）③人物关系网。

#### 5.4 用户与游戏化（PostgreSQL + Redis）

```sql
users(id, email, oauth_provider, created_at, ...)
user_profiles(user_id, lang, theme, ai_persona, level, level_name,  -- 童生/秀才...
              learning_stage, interests JSONB, locale, consent JSONB)
user_progress(user_id, streak_days, last_checkin, liuyi JSONB,       -- 六艺进度
              total_xp)
badges(id, name, tier, criteria)                                     -- 勋章定义
user_badges(user_id, badge_id, unlocked_at)
concept_collection(user_id, concept_id, unlocked_at)                 -- 图鉴收集
favorites(user_id, target_type, target_ref, created_at)             -- 收藏(句/卡片/视频)
conversations(id, user_id, created_at, mode)                        -- 对话会话
messages(id, conversation_id, role, content, citations JSONB,
         verify_scores JSONB, agents_used TEXT[], created_at)
```

> Redis 承载：连续打卡计数、排行榜（ZSET）、会话上下文短缓存、限流计数。

### 六、关键 API 契约（节选）


### 七、多语言与跨文化（后端职责）

1. **界面文案**与**内容**分离：界面 i18n 在前端；**经典内容译文**由后端从 `translations` 表按 `lang` 返回（权威译本优先，缺失时才由翻译智能体兜底生成并标注「AI 译」）。
2. **术语一致性**：所有儒家核心概念走 `concepts.i18n` 统一对照表，保证全平台「仁」始终呈现为 `Ren (仁) — humaneness / benevolence`，不让 LLM 每次自由发挥译法。
3. **跨文化解释智能体**用**结构化 prompt 模板**而非自由发挥，固定输出框架：古义 → 与社会秩序的关系 → 与自我修养的关系 → 与现代观念的差异 → 可现代转化/不可照搬的边界。对应方案中 "Is Li just social control?" 的标准回答骨架。
4. **敏感与价值边界**：跨文化/校验节点对涉及现代价值冲突的问题做「平衡说明」，并由内容审核（见下）兜底。

### 八、成本、性能与缓存

经典语料**有限且稳定**，这是最大的优化杠杆：

| 缓存层 | 内容 | 失效策略 |
|--------|------|----------|
| CDN 边缘 | 原文/拼音/译文/TTS 音频/图片 | 内容版本号变更才失效（近乎永久） |
| 概念解释缓存 | 每个概念在每种语言/模式下的标准解读 | 离线预生成 + 人工审核后冻结 |
| 语义缓存（Redis） | 「相似问题→已审答案」 | 向量相似度 > 阈值命中，TTL + 人工置顶 |
| 译文缓存 | AI 兜底译文 | 长期，待权威译本补入后替换 |
| TTS 预生成 | 高频经典句的多语言音频 | 离线批量，存对象存储 |

- **模型分级**：路由/分类/翻译用轻量模型；合成/校验用旗舰模型。LLM 网关按 `task_type` 路由。
- **预计算**：上线前离线跑一遍「每条 passage 的 AI 解读 + 每个概念的标准解释 + 高频追问」，把热路径变成查表。
- 目标：缓存命中类问答几乎零 LLM 成本、亚秒响应；只有真正新颖/个性化的问题才走完整智能体链。

### 九、语料治理与导入管线

数据质量 = 平台可信度。建议独立的离线管线（Celery 任务）：

```
原始文本（古籍/译本/注疏）
  → 清洗 + 结构化（书/篇/章/句切分，生成 ref_id）
  → 校对（人工抽检，权威版本对齐）
  → 拼音标注 + 概念标注（NER + 人工核对）
  → 多语种向量化 → 入 Milvus
  → 抽取人物/概念/命题/关系 → 入 Neo4j
  → 离线预生成 AI 解读/概念解释 → 人工审核 → 缓存冻结
  → 版本号 +1，灰度发布
```

> 关键：**经典原文与权威译注由人把关入库**，AI 只负责「解读层」且明确标注、可校验。这是与普通 RAG 玩具的本质区别。

### 十、安全、合规与审核

| 维度 | 措施 |
|------|------|
| 认证 | JWT + Refresh Token，OAuth（Google/Apple/微信） |
| 传输/存储 | 全链路 TLS，敏感字段加密，密钥走 KMS |
| 限流 | 网关按用户/IP 限流，LLM 调用单独配额防滥用 |
| GDPR/CCPA | `/me/export` 数据导出、`DELETE /me` 删除权、同意管理 `consent` |
| 数据驻留 | 多区域部署，欧盟用户数据留欧盟节点 |
| 日志脱敏 | 日志中 PII 脱敏，问答日志与身份分离存储 |
| 内容审核 | 输入/输出双向审核；多语言敏感内容过滤；涉政/价值冲突走平衡说明模板 |
| 提示注入防护 | 用户输入与系统 prompt 隔离，检索证据不可覆盖系统指令 |

### 十一、可观测与评估

- **链路追踪**：OpenTelemetry 贯穿网关→编排→各智能体；Langfuse 记录每次 LLM 调用的 prompt/输出/Token/延迟/成本。
- **质量评估**：建多语言评测集（问题→期望出处/要点），离线回归 + 在线抽样打分（忠实度/出处正确率/幻觉率/跨文化恰当性）。对应前端「校验徽章」的线下保障。
- **业务指标**：DAU、连击留存、概念收集率、追问点击率、各语言占比、各终端占比。
- **告警**：幻觉率、出处错误率、P95 延迟、LLM 成本异常。

### 十二、部署拓扑（全球）

```
用户 → Anycast/GeoDNS → 就近区域
   区域内：CDN → API Gateway → K8s 服务（无状态，HPA 弹性）
   数据：主区域 PostgreSQL（多区域只读副本）、Milvus、Neo4j
        Redis 区域内、对象存储跨区域复制
   LLM：按区域选可用模型服务端点（合规 + 低延迟）
```

- 无状态服务区域多活；强一致数据（用户/订单）单主多副本；经典内容只读、可全区域复制。
- 蓝绿/灰度发布，语料版本与服务版本解耦。

### 十四、后端创新点（呼应前端）

1. **证据绑定 + 校验闭环**：每条回答论断绑定 `ref_id`，校验节点核对真实性并产出三项评分 → 把"可追溯/可校验"做成系统机制而非口号。
2. **路由式智能体编排**：动态规划只激活必要智能体 + 并行扇出，兼顾"多智能体协同"的表达力与亚秒级的体验。
3. **经典语料的预计算与冻结**：把有限稳定的经典内容大规模预生成+人工审核+永久缓存，实现高质量与低成本兼得。
4. **权威分层**：原文/译注（人把关）与 AI 解读（可校验、明确标注）分层存储，杜绝"AI 发挥污染经典"。
5. **统一术语本体**：跨语言概念对照表保证全平台、全语种术语一致，避免 LLM 自由译法造成的文化误读。
6. **多端单后端**：终端差异收敛到「终端适配」投影层，一套 API 服务全部终端。
